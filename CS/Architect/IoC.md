# Inversion of Control

**Inversion of Control (IoC)** — принцип проектирования, при котором поток управления программы инвертируется: вместо того чтобы программист самостоятельно вызывал библиотечный код, фреймворк сам вызывает пользовательский код в нужные моменты.

Суть принципа описывается "голливудским правилом": *Don't call us, we'll call you* — "Не звони нам, мы сами позвоним". Программист описывает компоненты и точки расширения, а фреймворк берёт на себя ответственность за их вызов и связывание.

## Различие IoC и библиотеки

- **Библиотека** — набор функций, которые программист вызывает сам. Поток управления находится у прикладного кода.
- **Фреймворк** — предоставляет каркас и управляет потоком управления, вызывая пользовательский код через callback'и, обработчики событий или абстракции. Поток управления инвертирован.

## Пример: без IoC и с IoC

Без IoC — приложение само управляет всем:

```java
// Приложение само создаёт объекты и вызывает их
class App {
    void run() {
        Database db = new Database();
        UserRepository repo = new UserRepository(db);
        UserService service = new UserService(repo);
        service.processUser("alice");
    }
}
```

С IoC — фреймворк управляет созданием и вызовом:

```java
// Компоненты только декларируют зависимости
class UserService {
    private final UserRepository repo;
    UserService(UserRepository repo) { this.repo = repo; } // фреймворк сам внедрит
    public void processUser(String name) { ... }
}
// Фреймворк (контейнер) сам создаёт компоненты, связывает и вызывает их
```

## Частный случай

Один из частных случаев IoC — [[Dependency Inversion Principle]], который инвертирует именно направление зависимостей: высокоуровневые модули больше не зависят от низкоуровневых.

| Форма инверсии | Что инвертируется | Пример |
|----------------|-------------------|--------|
| Dependency Injection | Создание зависимостей | контейнер внедряет ссылки |
| Event-driven | Инициатор вызова | обработчик события вызывается фреймворком |
| Template Method | Алгоритм-скелет | hooks вызываются из базового класса |
| Strategy | Выбор алгоритма | стратегия подставляется извне |

## Реализации

Основные подходы к реализации IoC в контексте зависимостей:
- [[DI]] (Dependency Injection) — зависимости внедряются извне (push-модель)
- [[Service Locator]] — зависимости запрашиваются объектом самостоятельно (pull-модель)

Управление жизненным циклом объектов по принципу IoC берёт на себя [[IoC Container]].
